# DAX patterns and confirmed schema facts — Core model

Model: **Core Semantic Model** (`ded4bfa9-1961-4ac2-9b9c-cce085bf8ae1`). Pull this
file before writing non-trivial DAX against Core. For cross-model query
construction rules (DAX shapes, row-limit behavior), see `dax-patterns-general.md`.

## Confirmed facts — as of 2026-09-25

- Filtering through `DIM_DATE` propagates correctly to `FCT_OPPTYLINE_SPLIT`. The active relationship `DIM_DATE[DATE]` → `FCT_OPPTYLINE_SPLIT[DATE_CLOSE]` is unidirectional and correctly oriented: `CALCULATE(..., DIM_DATE[YEAR]=2025)` and the same measure filtered directly on `FCT_OPPTYLINE_SPLIT[DATE_CLOSE]` for the same range return identical row counts and sums. Filtering through `DIM_DATE` is safe to use.
- **For region/geo questions, filter via `DIM_REP[TERRITORY_REGION]`/`[TERRITORY_GEO]` (joined on `TERRITORY_ID`).** Core splits an opportunity's revenue across multiple sellers/territories (each row's `TERRITORY_ID` credits one seller their `SPLIT_PERCENTAGE`), and `DIM_REP` gives each row's credited seller's region/geo. That is how the business normally views region/geo, so it is the default for any "how is region/geo X doing" question. Use `DIM_OPPORTUNITY[REGION]`/`[GEO]` only when the user specifically asks for the opportunity's own region or geo. That is one value per opportunity, whichever sellers are credited, so it can differ from the credited seller's territory (a Georgia opportunity can credit a seller in New York 1 / East), and its region list is finer (East 1, East 2, Northeast). The two give materially different totals, so don't swap them.
- **`DIM_REP[TERRITORY_GEO]` values that read like one place are often several distinct string values, and the set changes over time** (a city can be split into numbered sub-territories, and territories get renamed or merged). A query that filters `TERRITORY_GEO = "<the name the user said>"` verbatim can silently return a blank result the moment the user's plain-English phrasing doesn't exactly match a currently stored value — and a blank result looks just as authoritative as a real one. Always confirm the live value set first — `FILTER(VALUES(DIM_REP[TERRITORY_GEO]), CONTAINSSTRING(DIM_REP[TERRITORY_GEO], "<name>"))` — rather than assuming the user's wording is the literal stored string, the same discipline as the `DIM_CUSTOMER` fuzzy-match rule above.
- **"Services" in a plain-English company-revenue question usually means the `FAMILY_STAMPED` values, not the separate Services Semantic Model.** `DIM_PRODUCT_STAMPED[FAMILY_STAMPED]` takes three values — `Product`, `Managed Services`, `Professional Services` — and cleanly partitions total revenue (confirmed: the family slices sum to the unfiltered total exactly, to the dollar). "Total company revenue including services" is answerable from Core alone: either the plain total (which already includes all three families) or, if the split itself is wanted, `FAMILY_STAMPED IN {"Managed Services","Professional Services"}` versus `"Product"`. Reach for the separate Services Semantic Model only when the question is actually about delivery-side data (timecards, practice, schedule, CSAT) — see "Picking the right model" in `SKILL.md`. Prefer `DIM_PRODUCT_STAMPED`'s stamped fields over `DIM_PRODUCT_CURRENT`'s current-taxonomy equivalents unless the question specifically wants today's reclassified view. Don't confuse `FAMILY_STAMPED` with `OFFERING_TYPE_STAMPED` — a different, more granular field (Accelerate, Advisory, as-a-Service, etc.) that also happens to contain service-sounding values but isn't the one this convention refers to.
- **Look up a named company in `DIM_CUSTOMER[CUSTOMER]` before assuming it doesn't exist or picking one match blindly.** Names rarely match exactly — e.g. searching "Acme" turns up `ACME Energy`, `Acme`, `ACME Markets Inc`, `Acme Paper & Supply Co., Inc.`, plus records like `Acme Truck Line Inc._Inactive` and `ACME - Test Record` that should usually be excluded from a real answer. When a search returns multiple plausible matches, show a best-guess result (if one candidate clearly has associated data) and ask which company was meant rather than silently picking one or reporting "not found."
- **Core now has the same `DIM_STAGENAME` lookup table as Specialty — use `DIM_STAGENAME[STAGENAME_TYPE] = "Closed Won"` to isolate closed-won activity, the same pattern as Specialty.** Confirmed to match the `Booked Revenue ACV` measure to the cent. `IS_BOOKING = TRUE` alone is still not a booking filter (see the pitfall in `SKILL.md`) — it needs the stage filter on top. If `DIM_STAGENAME` is ever missing from a schema pull, the equivalent hand-rolled filter is `STAGENAME IN {"Deal Booked","PO Received","Invoiced","Paid","Partially Invoiced","Vendor Accepted"}` (confirmed identical to the `DIM_STAGENAME` result) — `STAGENAME = "Deal Booked"` alone is **not** enough and significantly undercounts, since `DIM_OPPORTUNITY[STAGENAME]` reflects the opportunity's *current* stage and most booked revenue has since progressed into a post-booking fulfillment stage. Simplest and safest either way: use the "Booked X" measures directly rather than replicating this filter by hand.
- `DIM_OPPORTUNITY_SPLIT` (opportunity × team-member × role, with `SPLIT_PERCENTAGE`) has no data before 1/1/2024. 2024 itself carries only a small amount of data, skewed almost entirely to one role ("Client Director"), with effectively none tagged to some other roles (e.g. "Associate Client Director"). Full company-wide coverage across all roles starts in 2025 — don't assume a thin or blank 2024 result means "no data" without checking whether the date range or role is the actual cause.
- **"Who gets credit for this deal/customer" questions**: the territory on the opportunity (via `TERRITORY_ID` on `FCT_OPPTYLINE_SPLIT`) is the primary attribution mechanism. Break down by `TERRITORY_ID` joined to `DIM_REP[NAME]` to show each seller's share of a customer's or opportunity's credit (with `SPLIT_PERCENTAGE` and the relevant revenue/margin measure per seller) — this is the Core (CD-attribution) reading, and the default starting point unless the question is specifically about the Specialty sales-specialist overlay.
- `DIM_PRODUCT_STAMPED[IS_MS_STAMPED]` exists alongside `IS_IO_STAMPED`/`IS_SECURITY_STAMPED`/`IS_AI_CLOUD_STAMPED` as the Managed Services pillar flag, for hand-rolled pillar filters that need a boolean rather than `FAMILY_STAMPED`.

## Table/column naming

The live schema uses `DIM_OPPORTUNITY_SPLIT` and `DIM_OPPORTUNITY_TEAM` (DAX table names are case-insensitive, so this doesn't affect query behavior).
