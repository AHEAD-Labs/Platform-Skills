# DAX patterns and confirmed schema facts — Specialty model

Model: **Specialty Semantic Model** (`9500def1-be8b-4bbf-a4c5-6d458e1310ca`). Pull
this file before writing non-trivial DAX against Specialty. For cross-model query
construction rules (DAX shapes, row-limit behavior), see `dax-patterns-general.md`.

## Confirmed facts — as of 2026-09-23

- `SPECIALIST_ROLE` in `FCT_OPPTYLINE_SPECIALIST_SPLIT` takes exactly five values: `"Sales Specialist - Security"`, `"Sales Specialist - IO"`, `"Sales Specialist - Managed Services"`, `"Sales Specialist - AI"`, or `null` for lines with no specialist credit split tagged. `SPECIALIST_ROLE = "Sales Specialist - AI"` and `SPECIALIST_ROLE is blank` are two different, both-relevant conditions depending on the question — the pillar Booked measures use "blank or the pillar's role string" as their gate, not the role string alone.
- **Pillar Booked-margin measures are `Booked <Pillar> Commissionable Margin`, not `Booked <Pillar> Margin`.** Each is role-gated in the model itself: `Booked IO Commissionable Margin` is "Gated by `[_IO Commissionable Margin]`: `DIM_PRODUCT_STAMPED[IS_IO_STAMPED] = TRUE` AND `SPECIALIST_ROLE` is blank or `'Sales Specialist - IO'`... prevents Security/MS/AI specialist credit on IO-stamped product from being counted as IO." The same pattern holds for `Booked Security Commissionable Margin` and `Booked AI Commissionable Margin`. A sibling `Booked <Pillar> Gross Margin` also exists, using `GROSS_MARGIN_AMOUNT_ACV` (true gross margin) instead of the commissionable field. Use the built-in measures directly — no need to route around them with a hand-rolled role filter.
- **`Booked AI Commissionable Margin` uses `IS_AI`, not `IS_AI_CLOUD` — the two are different columns on `FCT_OPPTYLINE_SPECIALIST_SPLIT`, both present, not interchangeable.** A hand-rolled AI/Cloud query filtered on `IS_AI_CLOUD` instead of `IS_AI` will return a different (narrower) result than the official Booked AI measures.
- **FY2026 pillar Plan measures are guarded against product-filter collapse.** `2026 IO Plan`, `2026 Security Plan`, `2026 Net New/Only/Accelerate/Renewal/Total MS Plan`, and `2026 AI Plan` each wrap `REMOVEFILTERS('DIM_PRODUCT_STAMPED')` — without this guard, an unrelated product filter (e.g. an IO product filter) can collapse an unrelated pillar's plan to a small fraction of its correct value — this has been directly observed happening to Security's plan number. If a plan number looks too low, check whether a product-dimension filter is in play and whether the measure in question has this guard.
- **AI/Cloud has its own dedicated FY2026 plan and a full parallel measure set to Security/IO/MS.** `2026 AI Plan` is sourced from `FCT_SPECIALTY_CORP_PLAN` where `SOURCE = '2026_AI'` (its own dedicated full-year figure) and does not borrow `2026 IO Plan` (AHEAD's separate "Specialty Sales production report" apparently still does borrow IO's plan for AI — this model doesn't). `FY 2026 AI Delta to Plan`, `FY 2026 AI Go Get`, `FY 2026 AI Coverage Ratio`, and `FY 2026 AI Commissionable Margin Attainment %` are all present under those names.
- `DIM_DATE[MONTH_NUMBER]` is zero-padded text: `"01"` through `"12"`, plus a `null` row. Filtering `"6"` instead of `"06"` returns zero rows silently rather than erroring.
- `DIM_DATE[DATE]` → `DIM_OPPORTUNITY[DATE_CLOSE]` is unidirectional and correctly oriented, and the filter propagates through the chain to `FCT_OPPTYLINE_SPECIALIST_SPLIT`: filtering `DIM_DATE[YEAR]=2025` and filtering `DIM_OPPORTUNITY[DATE_CLOSE]` directly for the same range return identical row counts.
- `FCT_OPPTYLINE_SPECIALIST_SPLIT` is the correct grain for specialist-level analysis (revenue, margin, quota-retirement columns, split percentage). `DIM_OPPORTUNITY` is the right table for opportunity-header analysis (owner, stage, dates, pre-rolled totals) but doesn't carry the specialist split.
- **`Booked Revenue ACV` and `Booked Commissionable Margin` (the generic, non-pillar measures) filter `DIM_STAGENAME[STAGENAME_TYPE] = "Closed Won"` on top of `IS_BOOKING = TRUE`.** `DIM_STAGENAME` maps `STAGENAME` → `STAGENAME_TYPE` as: Closed Won = `{Deal Booked, PO Received, Invoiced, Paid, Partially Invoiced, Vendor Accepted}`; Pipeline = `{Prospecting, Pipeline, Upside, Strong Upside, Commit}`; Pipeline - Foundry = `{Discovery, Product Discovery, Product Proposal}`; Closed Lost = `{Closed Lost}`; and an oddball `10th System` → `10th System`. Core carries the same lookup table and the same mapping.
- **`DIM_STAGENAME`'s own table-level description text doesn't match its live data — trust the mapping above, not the table's self-description.** The description characterizes `STAGENAME_TYPE` as a three-way split ("Pipeline, Booked, Lost") and `STAGENAME_GROUP` as "Early Pipeline / Late Pipeline" buckets; the live data actually has five `STAGENAME_TYPE` values (as mapped above, using "Closed Won" rather than "Booked") and `STAGENAME_GROUP` values that are mostly 1:1 with `STAGENAME` for open-pipeline stages, only collapsing to a shared label for the Closed Won stages.
- **Managed Services has a Booked-measure sub-segmentation beyond the generic pillar pattern**: `Booked Net New MS Gross Margin`, `Booked Only MS Gross Margin`, `Booked Renewal MS Gross Margin`, `Booked Accelerate MS Gross Margin`, and `Booked Total MS Gross Margin` (each with Revenue ACV/TCV siblings). `Booked Total MS Gross Margin` = Only MS + Accelerate. `Booked Net New MS Gross Margin` scopes to `MODIFIED_FAMILY = 'Managed Services'` (family = Managed Services, offering type not Accelerate) plus `RENEWAL_TYPE_FOR_MS_SPECIALIST_ONLY = 'Net New'`. Exactly how `Net New` and `Renewal` compose `Only MS` hasn't been verified against a live sum — confirm before relying on that specific rollup in an answer.
- **Region/geo questions on Specialty filter through `DIM_TERRITORY`, not `DIM_REP`.** Specialists aren't aligned to a region/geo, so filter `DIM_TERRITORY[REGION]`/`[GEO]` (joined via `STAMPED_TERRITORY_ID`), which is the primary territory on the opportunity and the single value the deal belongs to. `DIM_TERRITORY[GEO]` is also the join target for `FCT_SPECIALTY_CORP_PLAN[GEO]`, so plan and specialist-split figures share the same region/geo path. `FCT_OPPTYLINE_SPECIALIST_SPLIT` also carries `OPPORTUNITY_REGION`/`OPPORTUNITY_GEO` (the parent opportunity's own region/geo); use them only when the user specifically asks for the opportunity's region or geo, which is rarely what a region/geo question means.
- **The `DIM_REP` join to `FCT_OPPTYLINE_SPECIALIST_SPLIT` is ID-based, not name-based.** Filter/join via `SPECIALIST_USER_SFID` ↔ `DIM_REP[USER_SFID]`. `SPECIALIST_NAME` is a denormalized display field only — don't join on it. `DIM_REP` no longer connects to `FCT_SPECIALTY_CORP_PLAN` at all; that table's `REGION`/`GEO` route through `DIM_TERRITORY` instead. `DIM_REP[TERRITORY_GEO]`/`[SPECIALIST_GEO]` are not the join target for the plan table anymore, even though they represent a conceptually similar geo.
