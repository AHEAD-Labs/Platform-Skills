# DAX patterns and confirmed schema facts — Services model

Model: **Services Semantic Model** (`85d404b7-1833-4163-8acd-1737776baa7f`). Pull
this file before querying Services. For cross-model query construction rules
(DAX shapes, row-limit behavior), see `dax-patterns-general.md`.

## Confirmed facts — as of 2026-09-22

- **CSAT, NPS, and quality-score data exist in `FCT_CSAT`**: `NPS_SCORE`, `CSAT_SCORE`, `IS_NPS_PROMOTER`, `IS_NPS_DETRACTOR`, `SCORE_BUSINESS_UNDERSTANDING`, `SCORE_ISSUE_RESPONSE`, `SCORE_QUALITY_OF_WORK`, `SCORE_SOLUTION_EXPERTISE`, `SCORE_OVERALL_SATISFACTION`, plus feedback metadata (`FEEDBACK_TYPE`, `IS_PARTNER_SURVEY`, `IS_EXCLUDED_FROM_REPORTING`, `DATE_REQUESTED`/`DATE_SUBMITTED`), linked to `PROJECT_ID` and `CUSTOMER_SFID`. None of these columns carry descriptions in the schema — confirm meaning with a live query (e.g. distinct values of `FEEDBACK_TYPE`) before building an answer on them.
- **"Early Warning" has no matching table, column, or measure anywhere in this model.**
- **Recognized revenue**: use `[Recognized Revenue (Monthly)]` / `FCT_PRACTICE_MILESTONE_FINANCIALS[RECOGNIZED_REVENUE]` — the authoritative source, covering 2020–present with both actuals and forecasts. **Do not use** `FCT_REVENUE_RECOGNITION_TRANSACTIONLINE[AMOUNT_RECOGNIZED]` for trend analysis — it only covers late 2024 onward and currently nets negative for 2025–2026 due to reversal entries; it's meant for auditing specific recognition events by milestone, not trending.
- **`PS_BACKLOG` / `[PS Backlog]` is a frozen September 2025 baseline, not current backlog.** Finance supplied that single month as the starting point when this backlog calculation was first built; from that point forward the real number is adjusted month-to-month using PSA data that lives outside this model, so this table has no visibility into anything since September 2025. A rebuild on Adaptive data is planned but not yet done. Treat `[PS Backlog]` as a historical anchor, not a current figure — don't present it as today's backlog. Its `REPORTEDBACKLOG` column is a formatted currency *string* and cannot be summed directly; the `[PS Backlog]` measure uses a parsed `REPORTEDBACKLOG_NUMERIC` calculated column internally. It joins to `DIM_PRACTICE` on the text label `PRACTICEL2` ↔ `DIM_PRACTICE[L2]`, not an ID, so practice-level backlog filtering can return unexpected results.
- **Don't hand-compute utilization by dividing `FCT_TIMECARD` hours by `FCT_CALENDAR_HOURS`** — the two tables cover different date ranges (`FCT_TIMECARD` 2019–present, `FCT_CALENDAR_HOURS` 2024–present). Use the built-in `[Billable Utilization Rate]` measure, documented as the authoritative utilization figure.
- `DIM_RESOURCE[DATE_TERM]` alone is not reliable for determining whether someone is still active — check `FCT_CALENDAR_HOURS[DATE_TERM]` (dated a year out for still-active people) or `DIM_RESOURCE[RESOURCE_ACTIVE]` instead. Don't trust a populated `DATE_TERM` on `DIM_RESOURCE` by itself to mean someone has left.
- **`DIM_PRACTICE`'s own description text doesn't match its live relationships — trust the relationship graph below, not the table's self-description.** `DIM_PRACTICE[PRACTICE_ID]` actively filters both `FCT_TIMECARD[RESOURCE_PRACTICE_ID]` (the resource's home practice) and `FCT_PRACTICE_MILESTONE_FINANCIALS[MILESTONE_PRACTICE_ID]` (the delivery/milestone practice), plus an inactive relationship `DIM_PRACTICE[PRACTICE_ID]` → `FCT_TIMECARD[MILESTONE_PRACTICE_ID]` that needs `USERELATIONSHIP` to activate. A resource can be home-based in one practice while delivering work billed under another milestone's practice — know which angle a question wants. `DIM_PRACTICE` has no relationship to `FCT_CALENDAR_HOURS` or `FCT_PLAN_BY_PRACTICE`; match those by their own `PRACTICE_L1_NAME`/`PRACTICE_L2_NAME` text columns. A practice-scoped question on `FCT_TIMECARD` or `FCT_PRACTICE_MILESTONE_FINANCIALS` can also be filtered via `FCT_TIMECARD[MILESTONE_L2_NAME]`, `DIM_PROJECT[PRACTICE_L1/L2/L3]`, or `DIM_MILESTONE[PRACTICE_L2]` as an alternative to the ID-based relationships.
- **Bookings measures here (`PS Booking TCV`, `MS Booking TCV`, `Services Booking TCV`) carry the same team-fan-out risk as Core/Specialty's opportunity-team tables.** `DIM_OPPORTUNITY_TEAM` → `FCT_OPPTYLINE_SPLIT` via `OPPORTUNITY_ID` averages multiple team-member rows per opportunity. Never `SUM` a bookings/financial measure filtered by any `DIM_OPPORTUNITY_TEAM` attribute (name, coverage, role) without accounting for the fan-out, or it will significantly overstate the number. Use `DISTINCTCOUNT` or a purpose-built measure instead.
- **Sales-to-delivery linkage path**: `DIM_PROJECT[OPPORTUNITY_ID]` connects a delivery project back to the Salesforce opportunity that originated it; `DIM_PROJECT` also carries `OPP_REVENUE`/`OPP_MARGIN` baseline columns copied from that opportunity at the time of handoff.
